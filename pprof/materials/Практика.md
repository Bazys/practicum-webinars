# Практика к вебинару «Профилирование в Go, использование pprof»

Сценарий рассчитан на 90 минут вместе с презентацией. Команды выполняются **из корня репозитория** в двух терминалах. На одном порту одновременно работает только один учебный сервер. После каждого демо остановите сервер через `Ctrl+C`, а перед следующим браузерным просмотром остановите предыдущий pprof / trace viewer.

## Подготовка до занятия

Понадобятся Go 1.26+ (требование `go.mod`), `curl`, браузер и два терминала. Для оформления PPTX установите YS Text из приложенного к задаче архива. Graphviz / `dot` нужен для Graph view, а текстовые `top`, `list`, `tags` и Flame Graph доступны без него.

```bash
go version
go env GOOS GOARCH
# Проверка команд до вебинара
go tool pprof -help
go tool trace -help
```

`GOMAXPROCS` задаётся runtime: зафиксируйте переменную окружения, если она задана, и суффикс `-N` у результата бенчмарка. Для условий эксперимента также запишите CPU quota, GOGC, GOMEMLIMIT, commit и число запросов.

В отдельных поставках Go отсутствует готовый бинарник trace. При наличии исходников стандартного toolchain его можно собрать локально без изменения установленного Go:

```bash
mkdir -p .pprof-demo/bin
go build -o .pprof-demo/bin/traceviewer cmd/trace
# Дальше вместо go tool trace используйте .pprof-demo/bin/traceviewer
```

Подготовим копии исходников с привязкой к loopback. Это сохраняет оригинальные примеры и не открывает учебные endpoints на внешних интерфейсах. Выполните блок один раз:

```bash
DEMO_DIR="$PWD/.pprof-demo"
mkdir -p "$DEMO_DIR/bin" "$DEMO_DIR/src" "$DEMO_DIR/profiles"

for name in example mutex labels trace; do
  sed -e 's/":8080"/"127.0.0.1:8080"/g' \
      -e 's/":8081"/"127.0.0.1:8081"/g' \
      "pprof/$name/main.go" > "$DEMO_DIR/src/$name.go"
  go build -o "$DEMO_DIR/bin/$name" "$DEMO_DIR/src/$name.go"
done
```

Оригинальные программы тоже запускаются через `go run ./pprof/example` и аналогичные команды на слайдах. Они слушают `:8080` / `:8081`; отдельный mux в `mutex` не ограничивает сетевой доступ.

Для команд ниже переменная не нужна: все пути приведены относительно корня. Заранее откройте исходники пяти примеров и `pprof/materials/benchmark/append_test.go`. Запасные результаты лежат в `pprof/materials/measurements/`.

## A. CPU и память: слайды 7–11

**Терминал 1:**

```bash
.pprof-demo/bin/example
```

Нагрузка работает непрерывно в `main.foo`; дополнительные запросы не нужны.

**Терминал 2:**

```bash
curl -fsS -o .pprof-demo/profiles/cpu.pb.gz \
  'http://127.0.0.1:8080/debug/pprof/profile?seconds=15'

go tool pprof .pprof-demo/bin/example .pprof-demo/profiles/cpu.pb.gz
```

Внутри pprof:

```text
top
top -cum
list main.foo
quit
```

Для браузера:

```bash
go tool pprof -http=127.0.0.1:9090 \
  .pprof-demo/bin/example .pprof-demo/profiles/cpu.pb.gz
```

Откройте VIEW → Flame Graph. Найдите ветку `main.foo`, раскройте `runtime.growslice` и `runtime.memmove`, если они попали в выборку. Проценты и порядок функций заранее не гарантированы. При большом числе функций runtime возвращайтесь к `list main.foo` и allocation profile. CPU-профиль не является распределением latency запросов.

Остановите viewer через `Ctrl+C`, оставив example работающим. Снимите **один** heap и смените только метрику:

```bash
curl -fsS -o .pprof-demo/profiles/heap.pb.gz \
  'http://127.0.0.1:8080/debug/pprof/heap?gc=1'

go tool pprof -top -alloc_space .pprof-demo/profiles/heap.pb.gz
go tool pprof -top -inuse_space .pprof-demo/profiles/heap.pb.gz
```

Ожидаем значительный вклад `main.foo` в выделение памяти. В `alloc_space` уже собранные объекты остаются в накопленной сумме. `inuse_space` зависит от фазы цикла и GC. Не требуйте совпадения цифр с подготовленным профилем.

Для аллокаций за окно:

```bash
curl -fsS -o .pprof-demo/profiles/allocs-window.pb.gz \
  'http://127.0.0.1:8080/debug/pprof/allocs?seconds=10'
go tool pprof -top -alloc_space .pprof-demo/profiles/allocs-window.pb.gz
```

**Ключевой разбор:** `/heap?seconds=30` возвращает delta, а не средний или пиковый heap. `/heap?gc=1` инициирует GC перед снимком и влияет на работу процесса. Heap указывает место создания, а не цепочку удерживающих ссылок.

**Запасной путь:** `go tool pprof -top pprof/materials/measurements/cpu.pb.gz`, `heap-alloc.txt`, `heap-inuse.txt`. Для `list` предпочтительнее свежий профиль с сохранённым бинарником и исходником той же сборки. После демо остановите example.

## B. Гипотеза и бенчмарк: слайды 12–14

```bash
go test -run='^$' -bench=BenchmarkBuild -benchmem -count=5 \
  ./pprof/materials/benchmark
```

Оба подбенчмарка строят один миллион целых чисел от 0 до `size-1`. `Grow` начинается с nil-слайса, `Prealloc` заранее резервирует capacity. `Result` делает результат наблюдаемым. `b.Loop()` требует Go 1.24+, что совместимо с требованием проекта. Сам исходный сервис использует 10 миллионов элементов, поэтому микробенчмарк не выдаётся за измерение времени HTTP-запроса.

Сначала сравните `B/op` и `allocs/op`, затем `ns/op` и разброс повторов. На слайде 13 показаны медианы пяти локальных прогонов. **Ускорение сервиса или p95 этим экспериментом не доказано.**

Для отдельных allocation profiles при одинаковом числе операций:

```bash
go test -run='^$' -bench='BenchmarkBuild/Grow$' -benchtime=100x \
  -memprofile=.pprof-demo/profiles/grow.pb.gz \
  -o .pprof-demo/bin/grow.test ./pprof/materials/benchmark

go test -run='^$' -bench='BenchmarkBuild/Prealloc$' -benchtime=100x \
  -memprofile=.pprof-demo/profiles/prealloc.pb.gz \
  -o .pprof-demo/bin/prealloc.test ./pprof/materials/benchmark

go tool pprof -alloc_space -top -base .pprof-demo/profiles/grow.pb.gz \
  .pprof-demo/profiles/prealloc.pb.gz
```

Профиль также включает служебные выделения тестового процесса. У двух функций разные стеки: в diff возможны отрицательные строки Grow и положительные Prealloc. Смотрите абсолютные суммы вместе с `B/op`, а не только доли. Профилированный прогон служит объяснению затрат; время сравнивайте отдельными запусками без профайлера и `-race`.

Для сравнения двух версий **одного** бенчмарка при одинаковых условиях удобно сохранить 10 повторов в `before.txt` и `after.txt`, затем использовать `benchstat before.txt after.txt`, если benchstat заранее установлен. Не устанавливайте инструменты во время вебинара. Документация: [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat).

**Вопрос:** почему `make([]int, size)` плюс прежний append меняет результат? Потому что слайс уже содержит `size` нулей. Здесь нужно `make([]int, 0, size)`.

## C. runtime/pprof: слайд 15

Оригинал `pprof/codeprofile` накапливает 100 миллионов `int`. На 64-битной машине логический объём элементов около 800 MB, а рост capacity и временные копии повышают пик. Для занятия используем уменьшенную копию и отдельные выходные файлы:

```bash
sed -e 's/100_000_000/1_000_000/g' \
    -e 's/99_000_000/990_000/g' \
    -e 's|pprof/codeprofile/mem.profile|.pprof-demo/profiles/mem.profile|g' \
    -e 's|pprof/codeprofile/cpu.profile|.pprof-demo/profiles/cpu.profile|g' \
    -e 's/":8080"/"127.0.0.1:8080"/g' \
    pprof/codeprofile/main.go > .pprof-demo/src/codeprofile.go

go build -o .pprof-demo/bin/codeprofile .pprof-demo/src/codeprofile.go
.pprof-demo/bin/codeprofile
```

**Терминал 2:**

```bash
curl -fsS 'http://127.0.0.1:8080/profile'
go tool pprof -top .pprof-demo/profiles/mem.profile
go tool pprof -top .pprof-demo/profiles/cpu.profile
```

Короткая работа может дать мало CPU samples или пустой CPU-профиль. Это часть разбора: для содержательного CPU-анализа уже есть длинное окно примера A. Не запускайте `/profile` одновременно из нескольких терминалов: CPU-профилирование глобально для процесса, а имена файлов фиксированы.

Покажите порядок `defer`: сначала завершение `StopCPUProfile`, затем закрытие файла. Heap сохраняется внутри цикла при достижении 990 000 элементов, перед возвратом из `foo`. `runtime.GC()` помогает получить свежий снимок, но меняет выполнение. Профиль CPU охватывает весь процесс за окно работы.

Для запуска оригинала команда `go run ./pprof/codeprofile` выполняется из корня. Он сохраняет файлы именно в `pprof/codeprofile/cpu.profile` и `pprof/codeprofile/mem.profile`, а не в корне.

После демо остановите сервер.

## D. Mutex, block и goroutine: слайды 20–21

**Терминал 1:**

```bash
.pprof-demo/bin/mutex
```

**Терминал 2:**

```bash
curl -fsS -o .pprof-demo/profiles/mutex.pb.gz \
  'http://127.0.0.1:8081/debug/pprof/mutex?seconds=10'
go tool pprof -top .pprof-demo/profiles/mutex.pb.gz

curl -fsS -o .pprof-demo/profiles/block.pb.gz \
  'http://127.0.0.1:8081/debug/pprof/block?seconds=10'
go tool pprof -top .pprof-demo/profiles/block.pb.gz

curl -fsS -o .pprof-demo/profiles/goroutine.txt \
  'http://127.0.0.1:8081/debug/pprof/goroutine?debug=2'
```

Откройте `goroutine.txt` и найдите `main.test`, затем `chan receive`. Здесь одна навсегда зависшая горутина, а не демонстрация бесконечного роста их числа. HTTP-сервер продолжает жить. Незавершившееся ожидание может ещё не учитываться в block-профиле.

В `add` / `get` критические секции очень короткие, Sleep(1 ms) находится вне mutex. Маленький или почти пустой mutex-профиль — допустимый результат. В block delta может быть видна работа самого HTTP handler, который ждёт окончания окна. Не интерпретируйте этот стек как проблему бизнес-кода.

**Необязательный контраст, если осталось время:** остановите сервер, скопируйте `.pprof-demo/src/mutex.go` в `.pprof-demo/src/mutex-slow.go`. Только в `add`, сразу после `mtx.Lock()`, добавьте `time.Sleep(2 * time.Millisecond)`. Соберите и запустите:

```bash
go build -o .pprof-demo/bin/mutex-slow .pprof-demo/src/mutex-slow.go
.pprof-demo/bin/mutex-slow
```

Повторите 10-секундный capture. Заранее объясните, что Sleep под lock намеренно усиливает конкуренцию и отсутствует в исходном примере. Mutex профиль ожидаемо укажет на стек освобождения в `add`, block — на ожидающие стороны.

**Запасной путь:** `measurements/mutex-top.txt`, `block-top.txt`, `goroutine.txt`. Остановите сервер.

## E. Labels: слайды 22–23

**Терминал 1:**

```bash
.pprof-demo/bin/labels
```

**Терминал 2, один блок:**

```bash
curl -fsS -o .pprof-demo/profiles/labels.pb.gz \
  'http://127.0.0.1:8080/debug/pprof/profile?seconds=15' &
capture_pid=$!
sleep 1

for i in $(seq 1 20); do
  curl -fsS -o /dev/null 'http://127.0.0.1:8080/profile/1'
  curl -fsS -o /dev/null 'http://127.0.0.1:8080/profile/1'
  curl -fsS -o /dev/null 'http://127.0.0.1:8080/profile/2'
done
wait "$capture_pid"

go tool pprof .pprof-demo/profiles/labels.pb.gz
```

Внутри pprof:

```text
tags
tagfocus=handler=^1$
top
tagfocus=
tagignore=handler=^1$
top
tagignore=
quit
```

`handler` — имя метки, `^1$` — точное строковое значение. Голое `handler=1` pprof может трактовать как числовой диапазон и ничего не выбрать. Запись `handler:1` из исходного README тоже подходит для этого примера, но фильтр с именем и regex показывает смысл явно.

Если tags пуст, нагрузка могла не попасть в окно. Повторите захват с большим числом запросов; не делайте вывод, что labels «не работают». Фоновый GC и runtime не обязаны иметь метку handler. Метки не дают latency запросов и не поддерживаются heap-профилем. В реальном сервисе используйте route pattern или тип задания с ограниченным набором значений.

**Запасной путь:** `go tool pprof -tags pprof/materials/measurements/labels.pb.gz` и тот же профиль с `-tagfocus='handler=^1$' -top`. Остановите сервер.

## F. Execution trace: слайды 25–26

**Терминал 1:**

```bash
.pprof-demo/bin/trace
```

**Терминал 2:**

```bash
curl -fsS -o .pprof-demo/profiles/trace.out \
  'http://127.0.0.1:8080/debug/pprof/trace?seconds=5' &
capture_pid=$!
sleep 1
for i in $(seq 1 6); do
  curl -fsS -o /dev/null 'http://127.0.0.1:8080/profile'
done
wait "$capture_pid"

go tool trace -http=127.0.0.1:9090 .pprof-demo/profiles/trace.out
```

При отсутствии установленной команды используйте подготовленный `.pprof-demo/bin/traceviewer` вместо `go tool trace`. В браузере найдите **User-defined tasks**, задачу `profileHandler` и регион `growSlice`. Названия разделов интерфейса зависят от версии toolchain. Сравните running, runnable и waiting, найдите пересечения с GC.

`createSlice` в исходнике содержит лишь `var slice []int`. Объявление не создаёт backing array. Основная работа находится в `growSlice`, несмотря на имя предыдущего региона.

Остановите viewer и покажите связь trace с pprof:

```bash
go tool trace -pprof=sched .pprof-demo/profiles/trace.out \
  > .pprof-demo/profiles/sched.pb.gz
go tool pprof -top .pprof-demo/profiles/sched.pb.gz
```

Типы извлечения: `sched` (задержка планирования), `sync`, `net`, `syscall`. Это не CPU-профиль. Для совместимости сохранённый trace лучше открывать той же или совместимой более новой версией Go. Подготовленная запись сделана Go 1.27.1; при Go 1.26 предпочтительнее снять свежую запись своим toolchain.

**Запасной путь:** `measurements/trace.out` и `sched-top.txt`. После демо остановите сервер и viewer.

## Технические акценты для докладчика

- `CPU samples` агрегируют CPU-стоимость стеков, а не задержку каждого запроса. Платформа и сборка влияют на детали выборки.
- `flat` — собственная стоимость, `cum` — со всеми вызываемыми функциями. Cum перекрывается между уровнями стека.
- `alloc_space` — накопленные байты, `inuse_space` — живые выделения с оговорками heap sampling / GC. Ни один из них не равен RSS.
- `seconds` у CPU/trace задаёт длительность записи. У heap, allocs, mutex, block и ряда других профилей HTTP handler возвращает delta.
- `SetMutexProfileFraction(1)` и `SetBlockProfileRate(1)` дают полный сбор учебных событий, но имеют разные единицы настройки.
- Отдельный mux не ограничивает сетевую доступность. У исходного mutex-примера адрес `:8081`.
- Метки наследуются новыми горутинами. Готовые worker pool требуют применения меток при выполнении задания.
- Исходники в `pprof` сохранены. Дополнительные варианты для эксперимента создаются в `.pprof-demo`.
